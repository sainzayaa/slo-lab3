Зөвхөн өөрийн локал машин дээрх серверийг (`http://localhost:3000`) тестэлсэн.

## Дахин ажиллуулах

```bash
npm install
node server.js            # тусдаа terminal дээр
mkdir -p results
k6 version
k6 run slo-test.js 2>&1 | tee results/pass.txt
k6 run --duration 2m slo-test.js 2>&1 | tee results/chaos.txt   # ажиллаж байх үед серверийг зогсоож 10 с дараа дахин асаана
k6 run slo-test-fail.js > results/fail.txt 2>&1; echo "exit=$?" | tee results/fail-exit.txt
```

## 1. Гурван чанарын сценарио (6 хэсэгтэй формат)

|---|---|

| Системийн төлөв | Сервер хэвийн ажиллаж байна, бүх endpoint идэвхтэй |
| Орчны төлөв | Хэвийн ачаалал: 20 зэрэгцээ хэрэглэгч (VU), нэг iteration ~1.3 с, ойролцоогоор 15 `/cart/add` хүсэлт секундэд |
| Гадаад өдөөлт | Хэрэглэгч `POST /cart/add` илгээнэ |

| Хэмжүүр | `/cart/add` latency-ийн p95 < 10 мс, 20 VU тогтмол ачаалалд 1 минутын дотор |

### Reliability сценарио

### Availability сценарио

| Хэсэг | Агуулга |

| Системийн төлөв | Сервер хэвийн ажиллаж байгаад crash болно |

| Гадаад өдөөлт | ЭВДРЭЛ: сервер процесс гэнэт зогсох (Ctrl+C), 10 секундийн дараа гараар дахин асаах |
| Шаардлагатай хариу | Зогсолтын үед хүсэлт буцаж (connection refused), дахин асмагц хүсэлтүүд дахин 200 болно |
| Хэмжүүр | Бүх хүсэлтийн амжилттай хувь (availability) ≥ 90%, 2 минутын цонхонд 10 с зогсолттой; сэргэх хугацааны зорилт 10 с (зогсолтоос дахин асах хүртэл) |

### Нэмэлт 4 дэх сценарио: тайлан

`/report` (200-400 мс-ийн санамсаргүй саатал) нь хэвийн ачаалалд p95 < 450 мс байх. Хэмжүүр: `/report` latency-ийн p95, 20 VU, 1 минут.

## 2. SLO хүснэгт

| Сценарио | SLI | Босго | Цонх / нөхцөл | Threshold (`slo-test.js`) |
|---|---|---|---|---|
| Performance | `/cart/add` latency p95 | < 10 мс | 20 VU, 1 мин | `'http_req_duration{name:cart}': ['p(95)<10']` |
| Reliability | `/pay` error rate | < 8% | 20 VU, 1 мин | `'http_req_failed{name:pay}': ['rate<0.08']` |
| Availability | Бүх хүсэлтийн амжилттай хувь (`checks`) | ≥ 90% | 2 мин, 10 с зогсолттой | `'checks': ['rate>0.90']` |
| Тайлан (нэмэлт) | `/report` latency p95 | < 450 мс | 20 VU, 1 мин | `'http_req_duration{name:report}': ['p(95)<450']` |

### Босго сонгосон үндэслэл

- **Performance < 10 мс:** localhost дээр `/cart/add` p95 нь 1.26 мс (`results/measure-initial.txt`) ба 1.36 мс (`results/pass.txt`) гарсан. Лабын жишээ 200 мс нь хэмжсэнээс ~150 дахин сул, юу ч илрүүлэхгүй. 10 мс нь ~7 дахин зайтай тул машины хэлбэлзэлд FAIL болохгүй, харин 10 дахин удаашрах регрессийг барина. (`p(95)<50` болгосон ч localhost дээр хэмжсэн 1.4 мс нь 35 дахин доогуур тул PASS хэвээр үлдэх байсан: энэ босго бодит аюулыг барихгүй.)
- **Reliability < 8%:** серверт ~5% алдаа суулгасан. 930 орчим хүсэлтийн санамсаргүй хэлбэлзэл ±2% тул 8% нь бодитой. Хэмжсэн: 5.68% (`measure-initial.txt`), 3.65% (`pass.txt`).
- **Availability ≥ 90%:** хэвийн үед checks = 98.78% (`pass.txt`; 1.2% нь `/pay`-ийн суулгасан алдаа). 90% нь 10% алдаа гаргах эрхийг үлдээнэ.
- **Report < 450 мс:** endpoint нь 200-400 мс саатдаг, хэмжсэн p95 = 393.25 мс (`pass.txt`). 450 мс нь ~14% нөөцтэй.

### Error budget

- **Цагаар:** 2 минутын цонхонд 90% = 10% × 120 с = **12 секунд** эвдрэх эрх.
- **Хүсэлтээр** (`results/chaos.txt`): нийт 5793 хүсэлт, 10% = **579 хүсэлт** алдаа гаргах эрх. Бодит алдаатай хүсэлт 1199 (20.69%) буюу budget-ээс ~2.07 дахин хэтэрсэн.
- **Яагаад хоёр тоо зөрж байна:** сервер унасан үед хүсэлт агшин зуур буцдаг (connection refused, 0 мс) ба `/report`-ын 200-400 мс хүлээлт алга болдог. Тиймээс iteration ойролцоогоор 1.0 с болдог (`chaos.txt`: `iteration_duration min=1s`), хэвийн үед ~1.3 с. VU бүр зогсолтын секунд бүрт ~3 хүсэлт гаргадаг, хэвийн үед ~2.3. Нэг зогсолтын секунд хэвийн секундээс ~30% илүү хүсэлт "иддэг". Жишээ нь 20 VU × 3 хүсэлт/с × 10 с ≈ 600 алдаатай хүсэлт, энэ нь 579-ийн хүсэлтийн budget-ийг ганц 10 с зогсолтоор бараг хэтрүүлнэ, харин цагийн 12 с budget-д багтана.

## 3. Алхам 4: threshold ба PASS гаралт

`results/pass.txt` (20 VU, 1 минут): бүх threshold ✓:

| Threshold | Үр дүн |
|---|---|
| `http_req_duration{name:cart}` p(95)<10 | p(95) = 1.36 мс ✓ |
| `http_req_duration{name:report}` p(95)<450 | p(95) = 393.25 мс ✓ |
| `http_req_failed{name:pay}` rate<0.08 | 3.65% ✓ |
| `checks` rate>0.90 | 98.78% ✓ |

## 4. Алхам 5: Chaos туршилт

`results/chaos.txt`: `k6 run --duration 2m slo-test.js`. Тест явагдаж байх үед серверийг Ctrl+C-ээр зогсоож, `sleep 10 && node server.js`-ээр дахин асаасан.

| Хэмжигдэхүүн | Үр дүн |
|---|---|
| checks (availability, хүсэлтээр) | **79.30%** (4594 / 5793) → ✗ FAIL (босго 90%) |
| `/pay` error rate (reliability) | **23.35%** (451 / 1931) → ✗ FAIL (босго 8%) |
| `http_req_failed` | 20.69% (1199 / 5793) |
| `/cart/add` p95 | 1.4 мс ✓ |
| `/report` p95 | 389.74 мс ✓ |

- **Бодит availability** = амжилттай / нийт хүсэлт = 4594 / 5793 = 79.30%. Error budget-ээ (579 хүсэлт) хэтэрсэн.
- **Бодит зогсолт 10 с-ээс урт байсан:** `/cart/add` дээр 373 хүсэлт амжилтгүй болсон; 20 VU × ~1 с iteration гэж үзвэл зогсолт ≈ 373 ÷ 20 ≈ 19 секунд (тооцоолол). `sleep 10` нь зөвхөн дахин асах хүртэлх хугацаа байсан, `Ctrl+C` дарснаас командыг paste хийх хүртэл ~9 с өнгөрсөн. Тиймээс цагийн 12 с budget-ийг ч хэтрүүлсэн, сэргэх хугацааны 10 с зорилт биелээгүй.
- **Latency threshold-ууд PASS хэвээр:** амжилтгүй хүсэлт 0 мс-ээр буцдаг тул p95 нь зогсолтыг илрүүлэхгүй.
- **Reliability ба availability нэг эвдрэлээр хоёулаа FAIL болсон**, учир нь сервер унасан үед `/pay`-ийн хүсэлт бүр унадаг. SLI-г салгахын тулд availability-г "хариу ирсэн эсэх" (status ≠ 0, connection refused биш), reliability-г "хариу ирсэн хүсэлтүүдийн 5xx хувь" гэж тусад нь тодорхойлж, тус бүрд нь өөр check/tag тавьж болно.

## 5. Алхам 6: Threshold-оо зориуд эвдэх

`slo-test-fail.js` нь `slo-test.js`-ээс зөвхөн `/report` threshold-оор ялгаатай: `p(95)<100` (сервер 200 мс-ээс хурдан хэзээ ч хариулдаггүй тул найдвартай FAIL болно).

- **`results/fail.txt`:** THRESHOLDS хэсэгт `✗ 'p(95)<100' p(95)=388.99ms` мөр гарсан (`/report` p95 = 388.99 мс > 100 мс). Гаралтын төгсгөлд `thresholds on metrics 'http_req_duration{name:report}' have been crossed` гэсэн алдааны мөр бий.
- **Exit code:** `results/fail-exit.txt` → `exit=99`. CI pipeline яг энэ exit code-оор build-ийг зогсооно.

## Дүгнэлт

1. Хамгийн хэцүү нь утга учиртай босго сонгох байсан: localhost дээр `/cart/add` p95 нь ~1.3 мс тул лабын 200 мс жишээ нь юу ч хэмжихгүй, тиймээс бодит хэмжилтээс (`measure-initial.txt`) 10 мс гаргасан.
2. Сценарио → SLO шилжилт нь энгийн, харин SLO → threshold-д метрик ба `name` tag-ийг яг таарахаар холбох шаардлагатай байсан.
3. Availability-г k6-ийн `checks`-ээр хэмжих нь төгс бус: хэвийн үед ч `/pay`-ийн суулгасан 500 алдаа `checks`-д орж 98.78% болгодог.
4. Хэвийн ажиллуулалтад 4 threshold бүгд PASS болсон (`pass.txt`).
5. Chaos туршилт availability SLO-г зөрчсөн (79.30% < 90%), мөн reliability SLO-г зөрчсөн (23.35% > 8%): нэг эвдрэл хоёр SLO-г зэрэг зөрчдөг.
6. Latency threshold-ууд зогсолтын үед PASS хэвээр байсан: амжилтгүй хүсэлт 0 мс-ээр буцдаг тул зөвхөн latency SLO нь outage-ийг үл анзаарна.
7. Цагийн error budget (12 с) ба хүсэлтийн budget (579 хүсэлт) зөрдөг: зогсолтын секунд хэвийн секундээс ~30% илүү хүсэлт "иддэг", ганц 10 с зогсолт хүсэлтийн budget-ийг бараг хэтрүүлнэ.
8. Бодит зогсолт ~19 с байсан (төлөвлөсөн 10 с-ээс урт) учир нь серверийг гараар дахин асаасан, тиймээс сэргэх хугацаа өөрөө автоматжуулах ёстой SLI юм (процесс хянагч, auto-restart).
9. Иймд chaos туршилт availability сценариогийн хэмжүүр хэмжигдэхүйц, зогсолтод мэдрэмтгий гэдгийг баталсан, харин гараар дахин асаадаг системд 90% зорилт биелэхгүй гэдгийг харуулж, SLO-г хэт өөдрөг байсныг илрүүлсэн.
10. Зориуд FAIL болгосон туршилт (`exit=99`) нь threshold-ыг CI-д build зогсоох хаалга болгон ашиглаж болохыг баталсан.
